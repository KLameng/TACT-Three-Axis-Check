# 贡献指南：社区 ratify 与真实案例回灌

本工具包的正确性验证遵循"开源后社区自发完成"的路线（不做需人工标注者的集中验证）。核心机制是 **ratify**：用真实事故案例逐步验证/修订坐标与判据。本文说明怎么提交真实案例、怎么判 ratify、怎么回灌数据。

## 1. 提交真实案例（怎么提交）

任何真实发生的 AI 系统失败/错误/异常，都可作为候选案例提交。**真实案例 = 非 synthetic、来自实际运行/实测环境、可回溯的现象记录。**

### 提交流程
1. 在 Issue 用以下模板提交；涉及敏感/隐私内容务必脱敏，**只描述现象，不含真实数据**。
2. 维护者/社区先做**初步判别**：用三步匹配法跑一遍，判断是否属于工具包可分类的机制。
3. 满足门槛后进入 ratify 流程。

### 提交模板（Issue）
```markdown
## 真实案例
- **现象**：发生了什么（客观描述，不含真实数据/凭据）
- **环境**：系统类型（单模型/智能体/RAG/多agent）、触发条件
- **观测**：模型/系统实际输出 vs 预期
- **是否可复现**：是/否，复现步骤（如有）
- **自评坐标**（可选）：L/M/P 自评 + 依据
- **保密声明**：已脱敏，无真实数据
```

## 2. 怎么判 ratify（核心规则）

### 坐标 ratify（转正）
- **预测格 → 正式码**：出现 **两条互不相干的真实案例** 同属该机制，即满足转正门槛（按"演进规则"）。
- **M9 自发协作**：母坐标已准入、子坐标待真实案例 ratified；同样以两条互不相干真实案例转正。
- **不 ratify 的条件**：synthetic 案例、同一事故的不同变体（不算"互不相干"）、疑似共享训练偏见的模型标注结果。

### golden 修订
- 真实案例与现有 golden 冲突时，以真实案例为准，**改 golden 并记 changelog**，不冻结。
- 修订后重跑校准集（回归模式），确认未静默漂移。

### 元标签 / 跨地图回灌
- 真实案例积累到 `E1`（1 案例）可标 `evidence_strength=E1`；`E2`（2 案例）/`E3`（≥3 案例）逐步升级。**不得虚报案例数**。
- 元标签按 `schema` 7 维补全，无案例用 `E0/E1` 并标记"待验证"。
- 跨地图映射只有 `verified`（有案例支撑）可引用；`hypothesis` 引用须标注"待验证"。

## 3. kappa 复验（怎么再测一致性）

每次改版 / 数据升版后，跑校准集重算 L/M/P 三轴 κ 与命中率，比对基线（见 `docs/TACT-kappa全历程汇总与分析.md` 的演进表）：

- **回归模式**：确认改动未引入静默漂移（与基线一致或更优）。
- **新增标注者**：社区可自选模型/真人跑同一校准集，提交 κ 结果；累计多样本后可替换/扩充当前 5 家大模型标注者。

## 4. 回灌边界（什么不该做）

- **不造码**：坐标增删只走"两条互不相干真实案例 + 结构校验"的演进规则，不自行新增子坐标。
- **不动 coordinate_data.json 的坐标语义**：判据修订走 SKILL.md，坐标语义保持稳定。
- **synthetic 不用于 ratify**：校准集仅测判别一致性，不视为真实事故，不用于坐标 ratify 证据。

## 5. 版本锁纪律

改工具包前先读 `guard/README.md`，走标准流程：`guard/unlock.sh` → 编辑 → 更新 `guard/MANIFEST.json` → `git commit` → `guard/lock.sh` → `guard/verify.sh`。受控文件（SKILL.md / calibration_cases.json / coordinate_data.json）被外部回滚时，用 `git restore` + `verify.sh` 恢复并报警。
